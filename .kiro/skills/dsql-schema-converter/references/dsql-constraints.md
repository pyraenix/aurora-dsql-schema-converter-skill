## Schema & Namespace Constraints

| Feature | DSQL Support | Notes |
|---|---|---|
| CREATE SCHEMA | Supported (max 10 schemas per database) | Admin users create schemas |
| GRANT USAGE ON SCHEMA | Supported | Admin grants access to other roles |
| Schema-qualified names | Supported | e.g., `myschema.mytable` works |
| search_path | Supported | May need connection refresh after DDL |
| DROP SCHEMA | Supported | Propagation may require reconnection |

**Important:** DSQL supports up to 10 schemas per database. This is different from PostgreSQL's unlimited schemas but sufficient for most applications. Admin users manage the public schema; non-admin users create objects in user-created schemas.

### Schema Behavior Notes

- After creating a new schema, GRANT/REVOKE changes propagate to existing connections within the connection lifetime (up to 1 hour)
- For immediate effect after permission changes, establish a new connection
- Refresh connection after creating/dropping schemas to ensure queries recognize new objects
- Some SQL clients (e.g., DataGrip) may show limited schema information

### IAM Authentication Model

DSQL uses AWS IAM for authentication combined with PostgreSQL database roles:
- Generate auth tokens via `aws dsql generate-db-connect-admin-auth-token`
- Tokens are short-lived (15 minutes)
- IAM roles are associated with database roles for SQL-level permissions
- Admin role is predefined and cannot be modified
- Custom roles are created with SQL and linked to IAM identities

### Database Role Types

| Role Type | Description | Created By |
|---|---|---|
| Admin | Predefined, manages public schema, creates other roles | System (automatic) |
| Custom | User-defined, associated with IAM roles | Admin via CREATE ROLE |

```sql
-- Create a custom role (admin connection required)
CREATE ROLE app_reader;
GRANT USAGE ON SCHEMA public TO app_reader;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO app_reader;
```

## Collation Constraints

| Aspect | DSQL Behavior | Impact |
|---|---|---|
| Database collation | C (fixed, cannot change) | Byte-order sorting |
| Per-column collation | COLLATE "C" only | No locale-aware sorting |
| Case sensitivity | Case-sensitive by default | Use lower() for case-insensitive |
| Unicode sorting | Byte-order (not UCA) | ä sorts after z, not after a |
| LIKE patterns | Byte-based matching | Works correctly for ASCII |
| ORDER BY text | Byte-order | Different results than en_US.UTF-8 |

### Behavioral Differences from PostgreSQL (en_US.UTF-8)

```sql
-- PostgreSQL (en_US.UTF-8): apple, Banana, cherry
-- DSQL (C collation):       Banana, apple, cherry  (uppercase first)
SELECT name FROM items ORDER BY name;

-- Workaround for case-insensitive sort:
SELECT name FROM items ORDER BY lower(name);
```

## Primary Key Design (Critical for DSQL)

DSQL stores data in primary key order (unlike PostgreSQL's heap storage). This has major performance implications:

### Key Design Rules

| Key Type | DSQL Behavior | Recommendation |
|---|---|---|
| UUID (random) | Distributes writes evenly | ✅ Best for most tables |
| Sequential/auto-increment | Creates hot spots | ⚠️ Avoid for high-write tables |
| Timestamp-based | Creates hot spots at recent end | ⚠️ Avoid as sole PK |
| Composite (tenant_id, uuid) | Good distribution within tenant | ✅ Good for multi-tenant |

### Why This Matters

```
-- PostgreSQL: heap storage, PK order doesn't affect write distribution
-- DSQL: PK-ordered storage, sequential keys = all writes to same node

-- BAD: Sequential ID creates hot spot
CREATE TABLE events (
  id bigint GENERATED ALWAYS AS IDENTITY,  -- sequential = hot spot
  ...
);

-- GOOD: Random UUID distributes writes
CREATE TABLE events (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),  -- random = distributed
  ...
);

-- GOOD: Composite key with random component
CREATE TABLE tenant_events (
  tenant_id bigint,
  event_id uuid DEFAULT gen_random_uuid(),
  PRIMARY KEY (tenant_id, event_id)  -- distributed within tenant
);
```

### Range Scans

PK-ordered storage means range scans on the primary key are physically sequential reads — much faster than in PostgreSQL. Design PKs to support your most common range queries.

## SELECT FOR UPDATE Behavior

`SELECT FOR UPDATE` is syntactically supported but behaves differently from PostgreSQL:

- Does NOT acquire row locks
- Does NOT block other transactions
- Conflicts are detected at COMMIT time (OCC)
- If another transaction modified the same rows, you get SQLSTATE 40001

**Migration impact:** If your app uses `SELECT FOR UPDATE` to serialize access to contested rows, those paths will surface as retryable OCC conflicts rather than blocking waits. Design for low contention and idempotent transactions.

## Sequence Constraints

| Constraint | Details |
|---|---|
| CACHE clause | Required (must be 1 or >= 65536) |
| Data type | BIGINT only |
| nextval(), currval(), setval() | All supported |
| lastval() | NOT supported (use currval with explicit name) |
| Gapless sequences | Not guaranteed (same as PostgreSQL with caching) |

### CACHE Value Selection Guide

| Use Case | CACHE Value | Rationale |
|---|---|---|
| Low-volume reference tables | CACHE 1 | Minimal gaps, low throughput OK |
| User-facing IDs (invoices, tickets) | CACHE 1 | Predictable numbering preferred |
| High-throughput tables (events, logs) | CACHE 65536 | Reduces round-trips to sequence server |
| Internal surrogate keys | CACHE 65536 | Gaps don't matter, performance does |
| Batch insert workloads | CACHE 65536 | Pre-allocates range for batch efficiency |

**Rule of thumb:** If you call `nextval()` more than 100 times/second, use CACHE 65536.

## Identity Column Support

DSQL supports identity columns as an alternative to SERIAL + sequence:

```sql
-- Preferred over SERIAL in DSQL
CREATE TABLE orders (
  id bigint GENERATED BY DEFAULT AS IDENTITY (CACHE 1),
  ...
);

-- GENERATED ALWAYS — prevents manual ID insertion
CREATE TABLE audit (
  id bigint GENERATED ALWAYS AS IDENTITY (CACHE 65536),
  ...
);
```

| Identity Type | Behavior | Use When |
|---|---|---|
| GENERATED BY DEFAULT AS IDENTITY | Allows manual INSERT of id | Migrating existing data with known IDs |
| GENERATED ALWAYS AS IDENTITY | Rejects manual INSERT of id | New tables, strict auto-generation |

### SERIAL vs Identity Column (Migration Choice)

| Approach | Pros | Cons |
|---|---|---|
| integer + explicit sequence | Full control, visible sequence | More DDL, manual wiring |
| GENERATED BY DEFAULT AS IDENTITY | Cleaner DDL, standard SQL | Less visible sequence management |

**Recommendation:** Use identity columns for new DSQL tables. Use explicit sequences when migrating existing data that references sequence values.

## Async Index Monitoring

Indexes created with `CREATE INDEX ASYNC` are not immediately usable. Monitor their status:

```sql
-- Check if all indexes are valid (built and ready)
SELECT schemaname, indexrelname, idx_scan
FROM pg_stat_user_indexes
WHERE indexrelname LIKE 'idx_%';

-- Check for indexes still being built
SELECT indexrelid::regclass AS index_name,
       indisvalid AS is_ready
FROM pg_index
WHERE NOT indisvalid;

-- If this returns rows, those indexes are still building.
-- Queries will work but won't use the index until indisvalid = true.
```

**Typical build time:** Seconds for small tables, minutes for millions of rows. No way to speed up — DSQL builds asynchronously in the background.

## Edge Cases in Type Handling

| PostgreSQL Expression | DSQL Behavior | Notes |
|---|---|---|
| NUMERIC (no precision) | numeric | Unbounded — stores up to 38,37 |
| VARCHAR (no length) | varchar | Treated as varchar(65535) |
| TIMESTAMP(3) | timestamp | Precision specifier preserved |
| TIMESTAMP(6) | timestamp | Microsecond precision (default) |
| CHAR (no length) | char(1) | Standard SQL behavior |
| DECIMAL | numeric | Alias — same type |
| FLOAT | double precision | Maps to 8-byte float |
| FLOAT(1-24) | real | 4-byte float |
| FLOAT(25-53) | double precision | 8-byte float |
